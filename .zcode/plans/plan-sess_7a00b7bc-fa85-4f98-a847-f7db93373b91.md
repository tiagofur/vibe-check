# Repos grandes + carpetas locales reales

## Diagnóstico (confirmado en código)

1. **GitHub >40MB**: `fetchTarball` (route.ts) descarga el tarball completo a un Buffer y lanza error si supera 40MB comprimido. Sin alternativa → el error de tu captura.
2. **Carpeta local**: el drag & drop (`filesFromDataTransfer` en page.tsx) **recorre `node_modules` entero llamando `.file()` por cada archivo antes de filtrar** → browser colgado con proyectos React. Y aunque pase, los topes son diminutos: 300 archivos / 900KB total / 40KB por archivo (cliente), 300 archivos / 80KB (servidor). Un proyecto real queda auditado a medias o vacío.

## A. GitHub de cualquier tamaño — descarga en streaming

Nuevo `src/lib/tar-gz.ts` (cero dependencias, como el resto del motor):

- **Parser tar incremental**: `fetch` con streaming → `Readable.fromWeb` → `zlib.createGunzip()` → parser de headers de 512B (ustar name+prefix, typeflag `0`/`x`/`g`/`L`, records pax para paths largos). Se procesa entrada por entrada sin cargar el tarball en memoria.
- **Estrategia single-pass**: cuenta TODAS las entradas (treeCount real) y guarda contenido solo del **top-120 por `riskScore(path)`** (heap con evicción — el mismo ranking que ya usa el triage). Guard: si descomprime >1.5GB → error claro. `contentHash` = sha256 del stream leído (caché intacta).
- **Se elimina el error de 40MB**: cualquier repo audita; el badge "árbol truncado" (ya existe) comunica honestidad. La descarga sigue siendo completa (el formato tar es secuencial) pero acotada en memoria y sin fallo. Timeout de descarga 45s→120s.
- **Modo diff**: mismo parser con presupuesto mayor (necesita árbol completo); si excede → mensaje claro, no un crash.

## B. Carpeta local — filtrar antes de leer + topes de verdad

- **Walker sin node_modules**: en `filesFromDataTransfer`, no descender a directorios pesados (`node_modules`, `.git`, `dist`,…) y tope de ~20k candidatos para no colgar el navegador. El `webkitdirectory` ya filtraba por path — se mantiene.
- **Topes alineados con el motor** (cliente = servidor): incluir archivos ≤256KB (truncando lectura a 64KB, igual que el CLI), hasta **800 archivos** y **8MB totales**. Server: zod `MAX_UPLOAD_FILES 800`, contenido ≤128KB, total 8MB, `MAX_SCAN_FILES 600`.
- **Feedback real**: toast "X archivos listos · Y omitidos (node_modules, binarios, grandes)" y texto del dropzone actualizado.
- Lógica de decisión extraída a `src/lib/folder-pick.ts` (pura) para testearla.

## C. Validación

- `tests/tar-gz.test.ts`: escritor tar mínimo dentro del test (ustar + pax longname + GNU 'L' + gzip real con zlib) → parseo, paths >100 chars, truncado por caps, evicción por riesgo, guard.
- Verificación local E2E: auditar por API un repo grande real — si la ingesta pasa, el error cambia de ">40MB" al de credenciales IA (que vive después), demostrando que el streaming funciona sin `.z-ai-config`.
- Suite completa: test/lint/typecheck/build. READMEs (es+en): sección "Límites honestos" actualizada.

El parser tar es lo más delicado: se cubre con tests de bytes construidos a mano (incluyendo pax/longname, que usan los tarballs de GitHub) y verificación contra un repo grande real. El modo diff queda con presupuesto amplio y error explícito si un repo gigante lo excede.
